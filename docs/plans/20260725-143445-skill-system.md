### 3. 需求演进与 Review 历史

**原始需求**（用户描述，概括保持原意）：

设计 skill 系统，主要三件事：

1. 在 system prompt 中注入默认的 `<skill-system>` 提示词（说明 progressive loading 模式：匹配到 skill 时用 `skill()` tool 加载、skill 文件可能引用同目录外部资源、按需加载、严格遵循 skill 指令）
2. 扫描当前目录 `.agents/skills` 下的 skill，以 `<available-skills><skill name="..." path="...">{description}</skill>...</available-skills>` 形式注入 system prompt
3. 实现一个 `skill` tool

**Review 阶段提出的技术问题**（只记录问题）：

1. Skill 系统的接入方式：自动启用、显式配置还是独立组装？
2. skill 提示词注入 system prompt 时，如何处理与现有 `syncSystemPrompt` 整体替换机制的交互（hook 修改 systemPrompt 会冲掉 skill 内容）？
3. 扫描格式：只认目录 + `SKILL.md`，还是也支持独立 `.md` 文件、递归嵌套？
4. frontmatter 解析：加 `gray-matter` 依赖、手写最小解析器，还是加完整 `yaml` 依赖？
5. `skill` tool 的接口设计：tool 名称、参数（是否支持 `args`）、返回内容（是否含 frontmatter、未命中行为、是否缓存）？
6. 扫描到坏 skill（解析失败、缺字段、name 与目录名不一致）时的容错策略？
7. 注入索引里的 `path` 用绝对路径还是相对路径？
8. `skills` 配置项的语义细节：默认目录、相对路径解析基准、配置形态？
9. skill 提示词的注入是否需要 hook 参与（每轮动态注入，或通过两段重组防止被 hook 改写冲掉）？

## Chapter 2: Detailed Technical Plan

### 1. Design Overview

```
AgentLoop 构造
  └─ resolveSkillsConfig(config.skills)         // false → 关闭；undefined/true → 默认目录；{ dir } → 自定义
  └─ scanSkills(absDir)                          // 扫 */SKILL.md → SkillInfo[]（容错跳过坏 skill）
  └─ skills.length > 0 时：
       ├─ skillPrompt = buildSkillPrompt(skills)        // <skill-system> + <available-skills>
       ├─ system message 内容 = [userSystemPrompt, skillPrompt].filter(Boolean).join('\n\n')
       └─ this.tools.push(createSkillTool(skills))       // skill(name) → 返回 SKILL.md 正文
```

注入只发生在构造时一次。`syncSystemPrompt` 保持现有的整体替换语义不变：hook 在 `userPromptSubmit` 中改写 `ctx.systemPrompt` 时，整条 system message（含 skill 段）被替换，这是可接受的边界行为，不做特殊保护。

核心数据流：模型返回 `tool_calls: [{ function: { name: 'skill', arguments: '{"name":"tdd"}' } }]` → agent-loop 按名查找 tool → `skill` tool 实时读对应 SKILL.md → gray-matter 剥离 frontmatter → 正文作为 `role: 'tool'` 消息进入下一轮循环（progressive disclosure 完成）。

关键测试 case：

- **正常流转**：模型发起 `skill` tool_call → 正文进入 messages → 下一轮模型拿到正文输出最终文本
- **异常分支**：模型请求不存在的 skill → 错误文本（含可用列表）进入 messages，agent 可自我纠正
- **边界条件**：hook 改写 `systemPrompt` → system message 被整体替换（skill 段随之移除，预期行为，不特殊处理）

### 3. Interface / API Design

**`src/skills/types.ts`**

```ts
export interface SkillInfo {
  /** skill 名，frontmatter name 缺失时以目录名兜底 */
  name: string;
  /** frontmatter description（缺此字段的 skill 被跳过） */
  description: string;
  /** SKILL.md 的绝对路径 */
  path: string;
}
```

**`src/skills/scan.ts`** — `scanSkills(dir: string): SkillInfo[]`

测试 case：

- S1（正常）：2 个合法 skill → 返回 2 项，`name`/`description` 与 frontmatter 一致，`path` 为绝对路径
- S2（边界）：`dir` 不存在 → 返回 `[]`，不抛错
- S3（边界）：子目录无 `SKILL.md` → 跳过；顶层独立 `.md` 文件 → 忽略（非目录）
- S4（异常）：frontmatter 非法 YAML（gray-matter 抛错）→ 跳过该项，其余正常返回
- S5（异常）：缺 `description` 或 description 非字符串 → 跳过
- S6（兜底）：缺 `name` → 以目录名为 name
- S7（优先级）：frontmatter `name` 与目录名不一致 → 以 frontmatter 为准
- S8（格式）：`description: >` 折叠多行 → 解析为完整单行文本（gray-matter 行为）
- S9（边界）：空目录 → `[]`

**`src/skills/prompt.ts`** — `buildSkillPrompt(skills: SkillInfo[]): string`

- P1（边界）：`[]` → 返回 `''`（调用方据此不注入、不挂 tool）
- P2（正常）：1 个 skill → 输出含 `<skill-system>` 固定提示词与 `<available-skills>`，`<skill name="..." path="...">` 属性正确，description 为标签体
- P3（正常）：多个 skill → 按数组顺序全部列出

**`src/skills/skill-tool.ts`** — `createSkillTool(skills: SkillInfo[]): Tool<z.ZodObject<{ name: z.ZodString }>>`

- `name: 'skill'`；description 说明"当用户请求匹配某个 skill 的用途时调用，传入 skill 名加载其完整指令"
- schema：`z.object({ name: z.string().describe('Skill name from <available-skills>') })`
- run：按 `name` 精确匹配 → 读 `skill.path` → gray-matter 剥离 frontmatter → 返回 `content.trim()`；未命中 → 返回 `Skill "<name>" not found. Available skills: a, b, c`

测试 case：

- T1（正常）：命中 → 返回正文，不含 `---` frontmatter
- T2（异常）：未命中 → 返回错误文本，包含所有可用 skill 名
- T3（契约）：`definition.function.name === 'skill'`，parameters 为 object 且必填 `name`
- T4（非法输入）：`execute({})` → zod 校验抛错（由 `Tool.execute` 既有行为保证）

**`src/agent-loop.ts`** — config 扩展

```ts
export interface AgentLoopConfig {
  model: Model;
  systemPrompt?: string;
  tools?: Tool<z.ZodSchema>[];
  hooks?: AgentLoopHooks[];
  /** 默认 true：扫描 <cwd>/.agents/skills；false 关闭；{ dir } 自定义目录（相对路径基于 cwd resolve） */
  skills?: boolean | { dir?: string };
}
```

构造时注入逻辑：system message 初始内容 = `[config.systemPrompt, skillPrompt].filter(Boolean).join('\n\n')`，非空才 push system message（与现有"无 systemPrompt 则无 system message"行为兼容）。`syncSystemPrompt` 代码不动。

集成测试 case（`tests/agent-loop/agent-loop-skills.test.ts`，用 `createMockModel` + 临时目录，通过 `skills: { dir }` 注入绝对路径避免依赖 cwd）：

- L1（默认开启+有 skill）：system message 同时含用户段与 `<available-skills>`；`tools` 含 `skill` tool
- L2（`skills: false`）：system message 仅用户段；无 `skill` tool
- L3（空 skill 目录）：system message 仅用户段；无 `skill` tool（与现状行为一致）
- L4（hook 整体替换，预期行为）：`userPromptSubmit` hook 改写 `ctx.systemPrompt` → system message 被整体替换为新值（skill 段随之移除，`syncSystemPrompt` 语义不变）
- L5（边界）：无 `systemPrompt` 但有 skill → system message 存在且仅 skill 段
- L6（端到端）：mock model 先返回 `skill` tool_call 再返回最终文本 → messages 中出现 `role: 'tool'` 的 skill 正文，run 返回最终文本

### 6. Risks & Mitigations

- **gray-matter 与 Rslib 构建的兼容性**：gray-matter 依赖 `js-yaml` 等，为 CJS 包。Rslib 默认能处理 CJS 依赖，build 后验证产物可 `import` 即可（Step 7 的 `pnpm run build` 覆盖）。
- **cwd 语义**：默认目录基于 `process.cwd()`，库被嵌入其他进程时 cwd 可能非用户预期 → 已通过 `{ dir }` 配置提供逃生门；集成测试一律显式传 `dir`，避免测试受 cwd 影响。
- **hook 改写 `systemPrompt` 会移除 skill 索引**：使用者若在 `userPromptSubmit` hook 中替换 systemPrompt，skill 段随之丢失（`skill` tool 仍在但模型看不到索引）。MVP 接受该行为并在本文档明确；有此需求的使用者可在 hook 中自行拼接 skill 提示词。回归测试：L4。
- **模型反复调用同一 skill**：实时读文件策略下每次返回相同内容，属预期行为，MVP 不做去重。
